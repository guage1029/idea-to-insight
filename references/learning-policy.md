# 定稿与自进化边界

## 每篇完成后的流程

1. 只有用户明确确认定稿，才调用 `memory_store.py finalize`。保存最终文章全文及其 SHA-256；不保存完整聊天或中间草稿。SQLite 唯一约束保证同一话题、同一文章 hash 不重复入账。
2. 结合用户对稿件的直接修改、明确的取舍/否定及其理由、反例处理反馈，提出 0 个或多个候选经验，并用 `finalize` 返回的 hash 绑定到具体文章。不得仅凭“定稿了”推断用户喜欢某种风格。
3. 每个候选必须包括规则、适用范围、触发条件、证据、例外；范围为本篇、某类文章、全局。默认只提出最窄有效范围。
4. 显示候选，让用户批准、修改或拒绝。批准前规则不影响活跃档案。
5. 用户批准后调用 `review-candidate --decision approve`。代码检查同范围/触发条件是否有冲突；冲突时保持候选 pending 并让用户裁定。批准后生成不可变的新档案版本。
6. 记录该次变化可回滚；无可靠增量、且没有待审/已激活候选时，调用 `no-new-rule`，为该定稿写入一条幂等的“本篇没有新增长期规则”事件。每篇定稿都有审计事件，但档案规则不必每篇变化。

## 代码保证与语义边界

代码可以保证定稿 hash 幂等、候选审批门禁、范围字段、冲突阻断、事件留痕、档案版本、回滚和导入导出校验。代码不能保证模型真正具备与用户完全相同的品味；语义回归只能给审核证据，不能自动批准规则。

## 持久化内容

- SQLite 保存话题检查点、状态、事件、必要短句证据、候选、批准后的档案版本，以及用户确认的最终文章全文。
- 不默认保存原始多轮对话或每轮草稿。
- 导出包包含最终文章全文和个人规则，应视为私人数据。POSIX 系统下目录为 `0700`、文件为 `0600`；不要将导出包发到公开位置。
- 失败的数据库检查、写入或导出必须明确报告；不得静默降级为“记住了”。
